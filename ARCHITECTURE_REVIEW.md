# Architecture Review
Generated: 2026-08-31T15:12:12.181Z

## Summary
The codebase is a well-documented Toss mini-app with strong conventions around pure calculation modules, TDS component guarding, and defensive WebView-SDK handling. However, it carries real architectural debt: a leftover 'contract.ts' spec file defines a second, incompatible entity model that some modules still import alongside the real 'types.ts' model, several UI primitives (EmptyState, SubmitFooter, SelectChip, haptic firing) are duplicated instead of shared, and state access is inconsistent — some pages go through the useLedger hook while others read/write localStorage directly, risking state desync.

## Issues
### Critical
- [duplication] Two incompatible entity/type systems coexist: src/lib/types.ts (the real app model: IncomeEntry, Platform w/ category+colorToken+archived, Settings w/ monthlyGoal) and src/lib/contract.ts (a generated spec model: Entry w/ amountKrw+hoursWorked, Platform w/ color+hourlyRate+isActive, Settings w/ theme+dailyGoalKrw). calc.ts imports IncomeEntry/Platform from types.ts for most functions but imports Entry from contract.ts for getDayStreak; validate.ts imports Entry/Platform from contract.ts. This makes it unclear which shape is authoritative and risks silent type mismatches when the two are ever used together. — Files: src/lib/contract.ts, src/lib/types.ts, src/lib/calc.ts, src/lib/validate.ts / Fix: Delete or archive contract.ts now that implementation is complete, and have calc.ts/validate.ts consume only src/lib/types.ts. If contract.ts must stay for codegen provenance, move it out of src/lib (e.g. into a docs/spec folder) so it can't be imported by runtime code.
- [consistency] Data access pattern is inconsistent across pages. Home.tsx, Entry.tsx, Report.tsx, and Share.tsx read/write state exclusively through the useLedger() hook (the documented single source of truth), but Platforms.tsx, Wage.tsx, and Settings.tsx call getPlatforms/savePlatforms/getEntries/getSettings/saveSettings directly from lib/storage, bypassing useLedger's in-memory state and derived-effects (e.g. bestStreak sync). Editing platforms in Platforms.tsx won't be reflected in Home.tsx's cached ledger state until a remount/navigation reload. — Files: src/pages/Platforms.tsx, src/pages/Wage.tsx, src/pages/Settings.tsx, src/hooks/useLedger.ts / Fix: Route all pages through useLedger() for platforms/entries/settings reads and writes; if a page needs actions the hook doesn't yet expose (e.g. archivePlatform edits, bulk delete), extend the hook's API rather than reaching into storage.ts from page components.

### Warnings
- [duplication] EmptyState is implemented twice with near-identical markup: src/components/EmptyState.tsx (title/description/action, hardcoded EmptyGlyph) and src/components/StateView.tsx's exported EmptyState (same, plus a customizable icon prop). Platforms.tsx uses the standalone EmptyState.tsx while Home.tsx, Entry.tsx, Report.tsx, Wage.tsx, and Sparkline.tsx all use StateView's EmptyState — and EmptyState.tsx itself imports EmptyGlyph from StateView.tsx, creating an odd one-directional coupling between two components serving the same purpose. — Files: src/components/EmptyState.tsx, src/components/StateView.tsx, src/pages/Platforms.tsx / Fix: Delete src/components/EmptyState.tsx and have Platforms.tsx import EmptyState from StateView.tsx like every other screen.
- [dead_code] src/components/SubmitFooter.tsx exports a 'SubmitFooter' component (plain Button + manual fixed-position/safe-area CSS), but every consumer (e.g. Entry.tsx) actually imports a same-named 'SubmitFooter' from src/components/BottomCTA.tsx (which wraps TDS FixedBottomCTA + haptic feedback). The standalone SubmitFooter.tsx appears unused anywhere in the codebase, duplicating both the name and the responsibility of BottomCTA's export. — Files: src/components/SubmitFooter.tsx, src/components/BottomCTA.tsx, src/pages/Entry.tsx / Fix: Remove src/components/SubmitFooter.tsx if confirmed unused, or rename/merge it if it serves a distinct non-tab-root use case; keep only one 'SubmitFooter' export in the codebase to avoid import-path ambiguity.
- [duplication] The 'fireHaptic' try/catch wrapper around generateHapticFeedback is reimplemented near-identically in six separate files (BottomCTA.tsx, ReportBody.tsx, Entry.tsx, Platforms.tsx, Wage.tsx, Settings.tsx) instead of being extracted once. — Files: src/components/BottomCTA.tsx, src/components/ReportBody.tsx, src/pages/Entry.tsx, src/pages/Platforms.tsx, src/pages/Wage.tsx, src/pages/Settings.tsx / Fix: Extract a single `fireHaptic(type)` helper (e.g. src/lib/haptics.ts or a `useHaptic()` hook) and import it everywhere instead of redefining the same try/catch block.
- [duplication] Entry.tsx defines a local 'SelectChip' component with a comment explicitly stating it has 'the same shape as SelectChip in /platforms', i.e. Platforms.tsx has its own near-identical copy. Both exist because TDS's ChipItem isn't mockable in tests, but the workaround was duplicated rather than shared. — Files: src/pages/Entry.tsx, src/pages/Platforms.tsx / Fix: Move SelectChip into src/components/ (e.g. SelectChip.tsx) and import it from both pages.
- [duplication] Validation limits are duplicated as separate magic-number constants: src/lib/constants.ts defines MAX_AMOUNT, MAX_MINUTES, MAX_PLATFORM_NAME, GOAL_MIN, GOAL_MAX for the whole app, while src/lib/validate.ts independently redeclares MAX_AMOUNT, MAX_MINUTES, MAX_PLATFORM_NAME_LENGTH, MIN_GOAL, MAX_GOAL with the same values. A future change to one file silently desyncs validation from the rest of the app (e.g. TextField maxLength vs validator limit). — Files: src/lib/validate.ts, src/lib/constants.ts / Fix: Import the shared constants from src/lib/constants.ts in validate.ts instead of redefining local copies.
- [naming] The identifiers STORAGE_KEYS and COLOR_TOKENS are each exported twice with conflicting shapes: constants.ts exports STORAGE_KEYS as a runtime object of localStorage keys and COLOR_TOKENS as a readonly array of color tokens; contract.ts exports STORAGE_KEYS and COLOR_TOKENS as *type* aliases with entirely different shapes (a key-map type and a semantic-color-role object type). Same names, different modules, incompatible meanings — easy to import the wrong one or search-confuse them. — Files: src/lib/constants.ts, src/lib/contract.ts / Fix: Once contract.ts is removed/relocated (see entity-model finding), this collision disappears; otherwise rename the contract.ts spec types to avoid colliding with real runtime exports (e.g. StorageKeysShape, ColorTokensShape).

### Suggestions
- [consistency] Import style for shared lib utilities is inconsistent: most files use the '@/lib/...' path alias, but Amount.tsx and CountUp.tsx import formatNumber via a relative path ('../lib/utils') instead. — Files: src/components/Amount.tsx, src/components/CountUp.tsx / Fix: Standardize on the '@/...' alias for all internal imports for easier refactors and consistent tooling/lint rules.
- [dead_code] src/lib/utils.ts exports 'cn' (classnames joiner) and 'formatCurrency' (Intl currency formatter), neither of which appears used anywhere in the codebase — components use inline style objects rather than className composition, and money formatting elsewhere goes through lib/format.ts's formatKRW/formatAmount. Similarly, src/lib/id.ts publicly exports both 'genId' and 'generateId' as an alias pair, but only 'generateId' is consumed by the rest of the app. — Files: src/lib/utils.ts, src/lib/id.ts / Fix: Remove unused exports (cn, formatCurrency, and the public genId export) or, if intentionally kept as public API surface, document their intended consumers to avoid accidental future duplication of formatting logic.
- [structure] types.ts (and constants.ts) declare empty `export const X = {} as const` 'existence marker' objects for every exported type purely so a test can assert the type was exported at runtime. This pattern doubles the export surface of every entity type (e.g. ColorToken exists as both a type and a same-named empty-object const, in two different files — types.ts and constants.ts) for no production behavior. — Files: src/lib/types.ts, src/lib/constants.ts / Fix: If this convention is only for a scaffold-verification test, move the markers into a dedicated test-support module instead of polluting the real type-definition files with parallel runtime exports.
- [naming] src/components/BottomCTA.tsx exports 'SubmitFooter' (and a second, unnamed multi-button component in its truncated middle section) — neither exported symbol matches the file name, unlike the rest of the components folder where file name and default/named export match 1:1 (Card.tsx→Card, ColorDot.tsx→ColorDot, SummaryHero.tsx→SummaryHero). Combined with the separate SubmitFooter.tsx file, this makes it hard to guess which file a given component lives in. — Files: src/components/BottomCTA.tsx / Fix: Rename BottomCTA.tsx to match its primary export, or rename the export to match the file, and ensure component filenames map predictably to their exports across the folder.
